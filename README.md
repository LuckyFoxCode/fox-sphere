# 🦊 FoxSphere

Modern full-stack monorepo for Twitch integration and streaming tools.

## Overview

FoxSphere is a self-hosted ecosystem that connects a Twitch channel to a set of
live overlay widgets, chat tools, and stream-economy features. The backend
subscribes to Twitch events and chats, pushes realtime data to clients over
Socket.io, while the frontend renders browser-source overlays for OBS / Streamlabs.

### Features

- **Chat & overlay widgets** — chat widget, timer, stream frame, and VIP widgets for the overlay
- **Pokémon overlay arena** — active Pokémon walk across the footer, with rank badges, role-colored borders, and chat message speech bubbles (with Twitch emotes)
- **Streamer XP system** — XP and levels driven by chat activity
- **VIP lottery** — automatic VIP giveaways from chat commands
- **Raid system** — raid command support
- **Stream events** — Twitch event subscriptions for live activity

## Monorepo Layout

```text
fox-sphere/
├── apps/
│   ├── bot-runtime/          # Twitch backend - Express + Prisma + Socket.io + the bot worker (deployed)
│   ├── overlay/              # Vue 3 overlay widgets for OBS (deployed)
│   ├── api/                  # Admin backend - Zod -> OpenAPI -> Swagger (local-only)
│   └── admin/                # Vue 3 admin panel, typed client generated by orval (local-only)
├── packages/
│   ├── types/                # Shared TypeScript types (@fox-sphere/types)
│   ├── shared-schemas/       # Shared Zod schemas & DTOs (@fox-sphere/shared-schemas)
│   ├── backend-shared/       # Prisma client, config, errors, logger (@fox-sphere/backend-shared)
│   └── db/                   # Prisma schema & migrations (@fox-sphere/db)
├── docs/                     # Guides & workflows
├── .docker/                  # Dockerfiles
├── .github/workflows/        # ci (the gate) + deploy
├── package.json              # Global scripts & orchestration
└── pnpm-workspace.yaml       # Workspace definition (apps/*, packages/*)
```

## Tech Stack

- **Monorepo:** `pnpm workspaces`
- **Frontend:** Vue 3 (Composition API) + TypeScript + Vite
- **Backend:** Express.js + TypeScript + `tsx` (TS Execute)
- **Database:** PostgreSQL + Prisma ORM
- **Realtime:** Socket.io
- **Twitch:** `@twurple` (chat, API, EventSub)
- **Linter/Formatter:** ESLint & Prettier
- **Infra:** Docker Compose, GitHub Actions, GHCR

## Getting Started

### Prerequisites

- Node.js 22.18+ or 24.12+ (CI and both images run 24; `apps/admin` enforces it via `engines`)
- pnpm 11 (`corepack enable` picks the version pinned in `packageManager`)
- Docker + Docker Compose (for PostgreSQL and backend hot-reload)

### Quick Start

```sh
# 0. First time only: dependencies, shared packages, Prisma client, migrations
pnpm install && pnpm build:p && pnpm prisma:g

# 1. PostgreSQL + the bot's HTTP server (hot reload) in the background
docker compose up -d
pnpm prisma:m

# 2. Twitch bot worker (in a separate terminal)
pnpm worker:t

# 3. Overlay for OBS
pnpm dev:f

# Optional: the admin panel - two more terminals, both local-only
pnpm dev:api      # admin backend + Swagger on :3001
pnpm dev:a        # admin frontend on :5174

# Optional: Prisma Studio to inspect the database
pnpm prisma:s
```

The overlay (`:5173`) is meant to be added to OBS as a Browser Source; the bot backend is
exposed on `:3000` (Socket.io + REST). The admin pair is not deployed - see
[`apps/api/README.md`](apps/api/README.md).

### Environment

- Dev: copy `.env.example` → `.env` (repo root; see `AGENTS.md` "First run") and fill Twitch credentials
- Prod: see `.env.prod.example` (used by `docker-compose.prod.yml` on the VM; never commit real values)

## API contract & codegen

The admin panel never hand-writes an API call. One route declaration in `apps/api`
produces the OpenAPI spec, and the spec produces a typed vue-query client for `apps/admin`:

```text
apps/api/src/modules/<feature>/<feature>.routes.ts     createModule() + route()
        │                                              (Express handler + Zod validation + OpenAPI path,
        │                                               declared once, in the same object)
        │  pnpm openapi:dump
        ▼
apps/api/openapi.json                                  committed - also served at /openapi.json,
        │                                              rendered by Swagger UI at /docs
        │  pnpm gen:api   (orval)
        ▼
apps/admin/src/api/generated/                          committed
        ├── channels/channels.ts                       useGetChannelById(), getChannelById()
        └── schemas/                                   Channel, ChannelStatus, ...
        │
        ▼
<script setup> in a component                          const { data } = useGetChannelById(id)
```

```sh
pnpm openapi:dump    # 1. routes  -> apps/api/openapi.json
pnpm gen:api         # 2. spec    -> apps/admin/src/api/generated/
```

Run both after adding or changing a route, in the same commit — CI fails the PR if either
artifact is stale. Neither step needs a running server: orval reads the committed
`openapi.json` file, not a URL.

- Writing a route (all verbs, validation, errors): [`apps/api/README.md`](apps/api/README.md)
- Consuming the generated hooks: [`apps/admin/README.md`](apps/admin/README.md)

## Docker & Deployment

- **Dev (`docker-compose.yml`):** PostgreSQL + backend in watch mode; frontend runs in the terminal.
- **Prod (`docker-compose.prod.yml`):** production stack driven by `.env.prod` on the target VM.
- **CI/CD:** every PR runs `.github/workflows/ci.yml` (the gate). Pushing to `main` runs it again, and `deploy.yml` follows on a green run: `linux/amd64` images are built, pushed to GHCR, and rolled out on the Oracle VM over SSH.

## Development Workflow & Releases

### Branch model

```text
feature/*  --(PR)-->  dev  --(PR)-->  main  --(tag)-->  vX.Y.Z
```

1. Create a feature branch from `dev` (`feat/DEV-<id>-<slug>`, `fix/DEV-<id>-<slug>`, `refactor/DEV-<id>-<slug>` — the Linear issue ID makes Linear link the branch to the issue automatically)
2. Open a PR into `dev`
3. Merge `dev` into `main`
4. Tag the release on `main`

### Conventional commits

Commit messages follow the conventional-commit format with the Linear issue ID prefix: `DEV-<id> type(scope): subject`

- `DEV-16 feat(...)` — new feature → minor release
- `DEV-16 fix(...)` — bug fix → patch release
- `DEV-16 docs(...)` — documentation only → no version bump
- `DEV-16 refactor(...)` — behavior-neutral refactor → patch release
- `DEV-16 feat(...)!:` / breaking change → major release

### Release tags (semver)

Releases are tagged on `main` only:

- `v1.0.0` — Twitch chat widget integration
- `v1.1.0` — Pokémon overlay & stream XP
- next fix → `v1.1.1`
